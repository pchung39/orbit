About ORBIT

Spacecraft anomaly investigation, with evidence you can review.

ORBIT brings telemetry, command history, procedures, and prior incidents into one investigation record. It helps an operator assess a possible cause, review the supporting evidence, and decide what to do next—including when to hold for more information.

I built ORBIT to explore a product question: what would make AI-assisted investigation useful to an operator and credible to the people reviewing the decision?

Current scope. A prototype using five simulated spacecraft scenarios. The browser demo runs a rules-based investigator. Experimental LLM providers are available through the command line. No flight data or operator-pilot results are claimed.

Similar alarms can require different decisions

The alarm’s shape alone cannot justify the same action in both cases. The investigation must account for the measurements and the procedure that governs the response.

I built the hold case first. It made the central requirement concrete: ORBIT must explain when the evidence is insufficient, even when a plausible answer is available.

RecordThree readers, one case

The product is a reviewable investigation

An operator needs a useful next step. A reviewer needs to understand why that step was recommended. The engineer maintaining the system needs to detect regressions before releasing a change.

ReaderNeeds from the record
OperatorA useful next step, including when to hold for more information.
ReviewerTo understand why that step was recommended, from the record alone.
MaintainerTo detect regressions before releasing a change.

ORBIT gives all three the same structured case record: the evidence considered, the calculations performed, the procedures cited, and the proposed conclusion.

That record is also what the evaluation suite checks. The tests inspect the output a user would actually review.

FlowEvidence in, command out

How an investigation works

  1. 01Preserve the evidence. When a case opens, ORBIT saves a fixed window of telemetry and events. The investigation works from that snapshot, so the original evidence remains available for review.
  2. 02Apply the relevant context. The investigator uses procedures and prior incidents to interpret the measurements. Procedure thresholds provide explicit criteria for evaluating a recommendation.
  3. 03Separate facts from explanations. The report identifies what was observed, what was calculated, what a document says, and what remains a hypothesis.
  4. 04Recommend a next step—or a hold. The case records a proposed action or explains why the available evidence does not support one. An operator reviews the result. ORBIT cannot send spacecraft commands.

Where the AI fits

The agentic problem is deciding what evidence to seek, which tools to use, and whether the results justify a conclusion. The tools retrieve or calculate evidence; the model’s role is to use that evidence to guide an investigation.

ORBIT separates the investigation workflow from the provider that performs it. The browser demo uses explicit rules to establish repeatable reference behavior. Separate LLM providers support command-line experiments with model-assisted investigation.

The published evaluation results below cover the rules-based provider. Running the model providers through the same checks is a next step. The current score does not establish model reliability.

These labels help a reviewer distinguish measurements from conclusions. A citation establishes where a claim came from; it does not, by itself, establish that the claim is correct or applicable to this case.

DesignSix constraints

The decisions behind the design

  • ReproducibleKeep each case reproducible. Evidence is saved with the case. A reviewer can return to the same snapshot instead of relying on a changing archive query. If more evidence is needed, the case boundary must be revisited explicitly.
  • ThresholdsTake thresholds from procedures. A model-generated explanation should not silently substitute a new threshold for the one specified in the procedure.
  • HoldMake a hold a complete result. When the evidence is insufficient, the report should state what is missing and avoid presenting a plausible cause as an established finding.
  • CaseOrganize the work around a case. Evidence, recommendations, and operator feedback belong in one persistent record that can be reviewed after the response window has passed.
  • No uplinkKeep spacecraft commanding outside the product. ORBIT supports investigation and records decisions. It has no command-uplink capability.
  • One vehicleStart with one simulated vehicle. Limiting the initial scope makes it possible to inspect the behavior in detail before expanding to more varied systems and operating conditions.
EvalFive scenarios · 55 checks

How I evaluate the system

The evaluation suite asks two questions: did the investigator reach the expected decision, and does the report support that decision appropriately?

For some cases, the expected result is a cause and a recommended action. For another, it is a hold, an explanation of the missing evidence, and no unsupported fault attribution. Both are testable outcomes.

Five scenarios, 55 checks

I created five simulated scenarios with known faults and decision criteria. Similar-looking cases require different recommendations, making them useful tests of whether the system applies the relevant evidence and thresholds.

The checks inspect the structured report, including evidence references, calculations, source labels, and recommendations. They do not inspect a model’s private reasoning or prove that it reasons correctly in general.

Check familyWhat it tests
OutcomeWhether the reported cause and recommended action match the expected result.
RefusalWhether the investigator holds when the threshold is unmet, explains the missing evidence, and avoids inventing a cause or fault identifier.
SourcingWhether claims have the required labels, calculations, and citations, with causal interpretations kept separate from observed events.
ContrastWhether the investigator avoids recommending a heater inhibit in cases where that action is inappropriate.

For example, one check rejects a report that introduces a fault identifier absent from the case evidence and cited procedure. An invented identifier can look authoritative even when the surrounding explanation is plausible.

What the current result means

The rules-based provider passes all 55 checks across the five simulated scenarios and passes the release gate against the stored baseline.

That result demonstrates compliance with the current test suite. It does not establish performance on unseen flight data, validate an LLM provider, or demonstrate readiness for operational use.

The Trust page exposes the individual checks and reads the same results artifact used by the release gate.

How the release gate works

A candidate build is compared with the accepted baseline by check family. Designated failures in refusal, sourcing, or contrast checks block release, even if the overall score improves.

Preserving the test evidence makes these comparisons interpretable: changes in the inputs cannot silently account for changes in the result. Model-based runs will also need repeated trials to measure variation between runs.

What I would test next

  1. Robustness to equivalent inputs. Change units or channel names without changing their meaning. Where the relevant evidence is preserved, the decision should remain consistent. Changes to time windows or noise levels need their own expected outcomes because they can alter the evidence.
  2. Ambiguous and misleading evidence. Add near-matching procedures, misleading prior incidents, missing telemetry, and cases with multiple plausible causes.
  3. Model-provider performance. Run LLM providers against the same requirements, repeat the runs, and report model results separately from the rules baseline.
  4. Independent scenarios and realistic data. Expand beyond cases developed alongside the investigator, then evaluate against reviewed historical incidents where access and permissions allow.

The current suite is a small regression suite. Broader coverage, independent cases, and realistic data are necessary to assess how well the design generalizes. Confidence calibration remains untested.

PilotNot yet run

How I would validate it with operators

ORBIT has not been tested with real operators. A pilot would begin with historical cases, progress to preparing reports for review, and reach live advisory use only after those earlier stages support it.

I would measure:

  • Time to a reviewable decision: compared with the existing investigation workflow.
  • Evidence completeness: how often operators need information outside the saved case.
  • Review quality: whether reports are accepted without substantive corrections.
  • Recommendation quality: when operators accept, reject, or revise a recommendation—and why.

An override rate alone cannot distinguish trust from overreliance. I would review the underlying decisions and evidence, including whether holds were appropriate.

Any recommendation judged inconsistent with the governing procedure would pause the pilot for investigation. The goal is faster, better-supported decisions, with appropriate holds when the evidence is insufficient.
