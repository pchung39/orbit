Design decisions

Spacecraft anomaly investigation, with evidence you can review.

ORBIT seals a telemetry window for each case, weighs the possible causes against the procedure that governs the alarm, and replays each option in a simulator before anyone acts. An operator sees what happened and why, decides what to do next—including holding for more evidence—and checks that the fix worked.

I built ORBIT to explore a product question: what would make AI-assisted investigation useful to an operator and credible to the people reviewing the decision?

Current scope. A prototype using five simulated spacecraft scenarios. Postgres holds only the case log—the case, its decision, and the simulated verification; tapes and procedures stay as files. The browser demo runs a rules-based investigator, and fix previews come from replaying the seeded simulator that generated each tape. Experimental LLM providers are available on the command line. No flight data or operator-pilot results are claimed.

The caseSame shape, different decision

Similar alarms can require different decisions

The alarm’s shape alone cannot justify the same action in both cases. The investigation must account for the measurements and the procedure that governs the response.

I built the hold case first. It made the central requirement concrete: ORBIT must explain when the evidence is insufficient, even when a plausible answer is available.

The hold case also keeps the simulator honest. Turning off the heater would lift the bus in the INC-0212 replay too, because removing a 2 A load always helps. That doesn’t make the heater the cause. ORBIT still recommends Hold and labels heater-off as EPS-17’s isolation test, which needs operator authorization.

RecordThree readers, one case

The product is a reviewable investigation

An operator needs a useful next step. A reviewer needs to understand why that step was recommended. The engineer maintaining the system needs to detect regressions before releasing a change.

ReaderNeeds from the record
OperatorA useful next step, including when to hold for more information.
ReviewerTo understand why that step was recommended, from the record alone.
MaintainerTo detect regressions before releasing a change.

ORBIT gives all three the same structured case record: the evidence considered, the calculations performed, the procedures cited, the explanations weighed and ruled out, the decision taken, and its simulated outcome.

The record follows the case through its lifecycle: open → needs decision → verifying or watching → closed. A case isn’t done when ORBIT recommends something; it’s done when the operator has decided and the result has been checked.

That record is also what the evaluation suite checks. The tests inspect the output a user would actually review.

FlowEvidence in, command out

How an investigation works

  1. 01Seal the window. When a case opens, ORBIT cuts a fixed window from the archive tape and writes it as a sealed file. The investigation reads that file, so later review sees the same evidence.
  2. 02Fetch the named procedure. The investigator reads the one procedure that governs this alarm (for example EPS-17) and the one prior the report cites. Procedure thresholds are the criteria for a recommendation.
  3. 03Weigh competing explanations. Heater, payload, and battery are each checked against the procedure bars, with evidence for and against. Each line of evidence links to the moment on the chart where it shows up.
  4. 04Prove it in a replay. Each tape is a seeded simulator run, so ORBIT can replay the window with the suspect fault removed, and with each option taken: turn off Heater B, safe the payload, or hold.
  5. 05Decide, verify, close. The operator approves an option or holds. ORBIT records the decision and checks the simulated outcome against the procedure’s recovery step; a hold stays open as Watching. ORBIT cannot send spacecraft commands.

Where the AI fits

The agentic problem is deciding what to sample from the sealed tape, which named document to read, and whether those results meet the procedure’s threshold. The tools retrieve or calculate evidence; the model’s role is to use that evidence to guide an investigation.

ORBIT separates the investigation workflow from the provider that performs it. The browser demo uses explicit rules to establish repeatable reference behavior. Separate LLM providers support command-line experiments with model-assisted investigation.

The published evaluation results below cover the rules-based provider. Running the model providers through the same checks is a next step. The current score does not establish model reliability.

The simulator is deliberately not AI. Replaying a seeded physics run reproduces the sealed tape sample for sample, so the only difference in a what-if is the one thing that was changed. Its results are labeled Simulated and never mixed with telemetry: a replay is evidence about ORBIT’s model of the spacecraft, not about the spacecraft itself.

OntologyWhat the record knows

ORBIT’s working ontology

ORBIT is built around a small, explicit set of kinds. The ontology is not a formal knowledge graph. It is the shared vocabulary that keeps telemetry, procedures, claims, and decisions from collapsing into one undifferentiated narrative.

If two statements look similar in prose, the ontology still asks: what kind of thing is being asserted, what evidence object supports it, and what decision object it is allowed to change?

Mission world

The simulated vehicle is described once, in a canonical mission model. Downstream tools reuse that model instead of inventing parallel channel names or limits.

KindRole in ORBIT
MissionThe simulated craft and operating context—here, Aurora-1.
SubsystemA functional grouping such as EPS, thermal, or payload.
ChannelA named measurable quantity with units, nominal range, and warn/critical limits.
LimitA threshold belonging to a channel or procedure, not a free-floating opinion.
Fault / modeA named physical or operational condition used by the simulator and scenarios. A recommendation may cite one; it must not invent one absent from evidence and procedure.

Evidence objects

ORBIT distinguishes the upstream archive from the evidence attached to a case. That distinction is what makes later review possible.

KindRole in ORBIT
Archive tapeAn upstream telemetry CSV. It remains outside the case unless a window is sealed from it.
Sealed snapshotThe fixed window written to runs/sealed/ with the case. Investigation reads this file, not a live archive query.
SampleA channel value at a time in the sealed window.
Event / commandA discrete logged action or mode change used to establish sequence.
ProcedureAn authored response file with explicit criteria, such as EPS-17’s ≥2× healthy-load bar. Fetched by id for the case.
Prior incidentA past close-out file used as context when the report cites it by id. Being named is not the same as being applicable.

Investigation objects

The case is the durable unit of work. Everything an operator or reviewer needs should hang from it.

KindRole in ORBIT
AlarmThe entry condition that opened the case—channel, time, and limit that crossed.
Case / incidentThe persistent record tying snapshot, report, explanations, decision, and verification together. It moves through a lifecycle: open, needs decision, verifying or watching, closed.
ClaimA statement about evidence or interpretation. Every claim carries a source label.
ExplanationA candidate cause—heater, payload, or battery—with its evidence for and against and a verdict: leading, below the bar, or ruled out.
RecommendationThe proposed next step, or a hold when the governing threshold is unmet.
ReplayA simulator run of the sealed window with one thing changed: the suspect fault removed, or an option taken. It is labeled Simulated and never treated as telemetry.
DecisionThe option the operator approved, with their reason and its simulated outcome. Choosing something other than the recommendation is recorded as a disagreement. It stores judgment; it does not uplink a command.

What the ontology is for

  • ReviewKeep kinds separable in the report. A reviewer should be able to tell whether a sentence is a sealed measurement, a calculation, a cited procedure step, or a proposed cause.
  • HoldMake missing evidence nameable. A hold is not a vague failure. It points at a missing kind—often a load that never cleared a documented threshold.
  • EvalGive tests stable targets. Outcome, refusal, and sourcing checks inspect these objects in the report a human would read, not private model reasoning.
  • BoundaryKeep commanding out of scope. Recommendation, decision, and replay are first-class. Spacecraft uplink is not an ORBIT object.

The next section covers the source labels that stamp each claim. Those labels are the epistemic layer on top of this ontology—how far a statement sits from measurement.

LabelsObserved to simulated

Every claim shows how it is supported

LabelMeaning
ObservedRecorded directly in telemetry or the command log.
DerivedCalculated from recorded evidence.
DocumentedSupported by a cited procedure or prior incident.
HypothesisA proposed explanation that requires interpretation.
SimulatedFrom a simulator replay of the sealed window. Evidence about ORBIT’s model of the spacecraft, not a measurement.

These labels help a reviewer distinguish measurements from conclusions. A citation establishes where a claim came from; it does not, by itself, establish that the claim is correct or applicable to this case.

On the case page, each label is backed by something you can open: evidence lines pin the moment on the chart, replays open inline beneath the claim they support, and an audit trail lists every read, calculation, and simulation in the order ORBIT ran them.

DesignTen constraints

The decisions behind the design

  • Case logKeep Postgres as a case log only. Incidents, decisions, simulated verification, and hypothesis feedback live in the database. Archive tapes, sealed windows, and procedures stay as files. ORBIT does not store a searchable document library or embeddings.
  • ReproducibleKeep each case reproducible. Opening a case writes a sealed window file. A reviewer returns to that file instead of relying on a changing archive query. If more evidence is needed, the case boundary must be revisited explicitly.
  • Named docsFetch the procedure the case already names. The investigator reads EPS-17, PAY-04, or EPS-09 by id, and the one prior the report cites. Similarity search over a document index is out of scope.
  • ThresholdsTake thresholds from procedures. A model-generated explanation should not silently substitute a new threshold for the one specified in the procedure. Today the rules encode those bars (EPS-17’s ≥2×) next to the investigator; reading them directly from the procedure files is the next step.
  • One ruleDecide the cause in one place. The report, the case page, and the decision record all use the same classifier, so the page can never disagree with the report it summarizes.
  • HoldMake a hold a complete result. When the evidence is insufficient, the report should state what is missing and avoid presenting a plausible cause as an established finding.
  • CaseOrganize the work around the case lifecycle. A recommendation is the middle of a case, not the end. The record carries the evidence, the explanations weighed, the decision, and whether the fix held, and it can be reviewed after the response window has passed.
  • ReplayProve it before acting, and label the proof. Previews come from replaying the seeded simulator that produced the tape, with one change at a time. They are tagged Simulated, shown beside the claim they support, and never mixed with telemetry.
  • No uplinkKeep spacecraft commanding outside the product. ORBIT supports investigation, records decisions, and verifies them in simulation. It has no command-uplink capability.
  • One vehicleStart with one simulated vehicle. Limiting the initial scope makes it possible to inspect the behavior in detail before expanding to more varied systems and operating conditions.
EvalFive scenarios · 55 checks

How I evaluate the system

The evaluation suite asks two questions: did the investigator reach the expected decision, and does the report support that decision appropriately?

For some cases, the expected result is a cause and a recommended action. For another, it is a hold, an explanation of the missing evidence, and no unsupported fault attribution. Both are testable outcomes.

Five scenarios, 55 checks

I created five simulated scenarios with known faults and decision criteria. Similar-looking cases require different recommendations, making them useful tests of whether the system applies the relevant evidence and thresholds.

The checks inspect the structured report, including evidence references, calculations, source labels, and recommendations. They do not inspect a model’s private reasoning or prove that it reasons correctly in general.

Check familyWhat it tests
OutcomeWhether the reported cause and recommended action match the expected result.
RefusalWhether the investigator holds when the threshold is unmet, explains the missing evidence, and avoids inventing a cause or fault identifier.
SourcingWhether claims have the required labels, calculations, and citations, with causal interpretations kept separate from observed events.
ContrastWhether the investigator avoids recommending a heater inhibit in cases where that action is inappropriate.

For example, one check rejects a report that introduces a fault identifier absent from the case evidence and cited procedure. An invented identifier can look authoritative even when the surrounding explanation is plausible.

What the current result means

The rules-based provider passes all 55 checks across the five simulated scenarios and passes the release gate against the stored baseline.

Separate unit tests cover the case page’s data: the cause it shows matches the report, every current quoted in an evidence line is a sample on the tape, load attribution adds up to the measured bus current, and each simulator replay reproduces its archive tape exactly before any change.

That result demonstrates compliance with the current test suite. It does not establish performance on unseen flight data, validate an LLM provider, or demonstrate readiness for operational use.

The eval harness exposes the individual checks: python -m eval writes the same results artifact the release gate reads.

How the release gate works

A candidate build is compared with the accepted baseline by check family. Designated failures in refusal, sourcing, or contrast checks block release, even if the overall score improves.

Preserving the test evidence makes these comparisons interpretable: changes in the inputs cannot silently account for changes in the result. Model-based runs will also need repeated trials to measure variation between runs.

What I would test next

  1. Generated variants. Use the simulator to generate hundreds of variations—heater draw from 1.2× to 3.5×, noise, shifted confounders, two faults at once—and report accuracy against fault size, so the weak spot near the 2× bar is visible instead of hidden behind five hand-built cases.
  2. Robustness to equivalent inputs. Change units or channel names without changing their meaning. Where the relevant evidence is preserved, the decision should remain consistent. Changes to time windows or noise levels need their own expected outcomes because they can alter the evidence.
  3. Ambiguous and misleading evidence. Add near-matching procedures, misleading prior incidents, missing telemetry, and cases with multiple plausible causes.
  4. Model-provider performance. Run LLM providers against the same requirements, repeat the runs, and report model results separately from the rules baseline.
  5. Independent scenarios and realistic data. Expand beyond cases developed alongside the investigator, then evaluate against reviewed historical incidents where access and permissions allow.

The current suite is a small regression suite. Broader coverage, independent cases, and realistic data are necessary to assess how well the design generalizes. Confidence calibration remains untested.

PilotNot yet run

How I would validate it with operators

ORBIT has not been tested with real operators. A pilot would begin with historical cases, progress to preparing reports for review, and reach live advisory use only after those earlier stages support it.

I would measure:

  • Time to a reviewable decision: compared with the existing investigation workflow.
  • Evidence completeness: how often operators need information outside the saved case.
  • Review quality: whether reports are accepted without substantive corrections.
  • Recommendation quality: when operators accept, reject, or revise a recommendation—and why.
  • Preview fidelity: how often the simulated outcome of an approved option matches what the spacecraft actually did once the operator sent the command.

An override rate alone cannot distinguish trust from overreliance. I would review the underlying decisions and evidence, including whether holds were appropriate.

Any recommendation judged inconsistent with the governing procedure would pause the pilot for investigation. The goal is faster, better-supported decisions, with appropriate holds when the evidence is insufficient.
